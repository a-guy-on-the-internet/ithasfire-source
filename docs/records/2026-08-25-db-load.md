# Database Load — 2026-08-25

One-off investigation into production Postgres query volume, and a ranked plan
to reduce it. Point-in-time, unlike `resource-burn.md`: nothing regenerates this
file, so treat the numbers as a dated snapshot rather than a live report.

**Window:** 7d · **Env:** `production` · **Source:** Sentry spans, project
`hearth-fire-web` · **Multiplier:** 0.907 (verified, see below)

---

## Read this before trusting any `span.op:db` number

Two distortions sit between `span.op:db` and "queries". `resource-burn.md`'s
Neon row (555,530 queries, 79,361/day) is subject to both and is roughly 2×
high as a result.

**Every SQL statement emits exactly two spans.** Prisma's OTel instrumentation
and the `pg` OTel instrumentation are both active, and both fire on the same
statement.

| `sentry.origin`         |   spans | what it is                                                             |
| ----------------------- | ------: | ---------------------------------------------------------------------- |
| `auto.db.otel.postgres` | 184,900 | SQL + BEGIN + COMMIT                                                   |
| `auto.db.otel.prisma`   | 172,590 | SQL + COMMIT (no BEGIN)                                                |
| `manual`                | 190,590 | `pg-pool.connect` + `pg.connect` — connection bookkeeping, not queries |

Subtract transaction control from each origin and both land on **160,290**,
matching to the row. That is the true statement count.

Cleanest query: filter `sentry.origin:auto.db.otel.postgres`, subtract BEGIN and
COMMIT. No halving needed on that one origin.

**`pg-pool.connect` wraps `pg.connect`.** They nest. Summing them double-counts.

### Verifying the sampling multiplier

Counts are always multiples of 10 — Sentry extrapolates a 10% sample. The
extrapolation is accurate: **0.907** measured against the known cron ceiling,
per-job ratios clustering 0.87–1.19. Absolute weekly figures hold to within
about 10%.

The trap: compute the ceiling from the **deployed** crons, not the manifest.
`jobs_scheduler_overrides` in `infra/terraform/envs/prod/prod.tfvars` retunes 9
crons far below `apps/jobs/jobs.manifest.json` (the 2026-07-30 retune, 3,591 →
1,635 runs/day). Using the manifest alone yields a bogus 0.43 and discredits
every absolute number in the report.

## Where the time actually goes

|                                              |       ms/week |
| -------------------------------------------- | ------------: |
| `pg.connect` — establishing connections      | **3,045,955** |
| all SQL execution combined (postgres origin) | **1,421,587** |

Connection setup costs 2.1× more than every query in the system put together.

Individual queries run in 5–10ms almost regardless of what they do — a
`WHERE id IN (NULL)` that can never match a row takes 5.8ms, the same order as
the ranked-search CTE at 10.7ms. That is Neon round-trip latency, not work.

**Round-trips are the unit of cost here, not query complexity.** Each SQL
statement takes its own pool acquisition — verified 1:1 on `GET /trpc/:path`,
80,940 acquisitions against 80,940 statements — and 39% of acquisitions pay a
~57ms handshake.

### Why so many handshakes

`apps/api/src/lib/dep.ts:622`:

```ts
const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
```

No `idleTimeoutMillis`, no `max`, no `connectionTimeoutMillis`. The `pg` default
for `idleTimeoutMillis` is **10 seconds**. Production runs ~1.7 tRPC
requests/minute — a ~35s mean gap — so idle connections are reaped between
essentially every request. On `GET /trpc/:path` that means 2.51 fresh handshakes
per request, ~143ms of pure connection setup on every homepage render.

Reproduced locally against Postgres with the same `PrismaPg` adapter, two
queries separated by a 12s gap:

```
DEFAULT (idleTimeoutMillis=10000)      physical TCP connects = 2
idleTimeoutMillis: 0  (never expire)   physical TCP connects = 1
idleTimeoutMillis: 60000               physical TCP connects = 1
```

Latent, not yet biting: pool `max` defaults to **10** while the Cloud Run service
sets no `max_instance_request_concurrency`, so Cloud Run's default of **80
concurrent requests per instance** applies. At current volume this never
saturates. Under a burst, requests queue on the pool with no
`connectionTimeoutMillis` to bound the wait.

## Who is generating the traffic

Not crawlers hitting the API — the web tier hitting the API.

98.9% of tRPC GETs carry `user_agent: node`, and `client.address` resolves to
`2600:1900:0:35xx::`, Google Cloud IPv6. That is the web Cloud Run service.
SSR targets the internal `*.run.app` origin directly and by design
(`apps/web/src/server/origin-secret.ts:10`), so **this traffic never passes
through Cloudflare and cannot be CDN-cached.**

Two URLs are effectively all of it:

```
/trpc/features.getFeatureGates,events.countryEvents,search.featuredEvents   12,320
/trpc/features.getFeatureGates                                               4,860
                                                                     = 17,180 / 17,410
```

What drives those renders is unresolved. The evidence points hard at automated
traffic but does not close the case:

- ~150 browser `pageload`/`navigation` transactions per week against 17,180
  homepage SSR renders. Browser and server SDKs both run `tracesSampleRate: 0.1`.
  Real browsers loading the page would fire a pageload.
- Hourly volume is flat around the clock. 06Z–10Z (1–5am Central) runs
  50/80/150/90 — no diurnal dip.
- Forwarded end-user geo on `countryEvents`: us 5,710, **br 2,290, sg 2,070,
  be 2,070**. Brazil, Singapore and Belgium each out-volume every other market
  for a Nashville-focused platform.

`apps/api/src/instrument.ts` drops bots in `beforeSend` but not
`beforeSendTransaction`, and the identifying UA is replaced at the web tier
before the API sees it. To settle it: read Cloudflare bot-score analytics on the
web hostname, or attach the forwarded UA to `beforeSendTransaction`.

## Ranked plan

Ranked by (queries saved) / (risk × effort). Ordering is the point, so the
numbers matter.

### 1. Set pool `idleTimeoutMillis` and `max` — DONE (local, undeployed)

Shipped as `POOL_TUNING` in `packages/db/src/pool-config.ts`, applied to all four
pool sites: `apps/api/src/lib/dep.ts`, `apps/jobs/src/lib/container.ts`,
`apps/audio-transcoder/src/lib/container.ts`, `packages/db/src/index.ts`.

Recovers 53,380 cold handshakes/week — **3,046 s/week, 2.1× all query execution**
— and ~143ms off every homepage request. One line.

```ts
export const POOL_TUNING = {
  max: 10,
  idleTimeoutMillis: 60_000,
  connectionTimeoutMillis: 10_000,
};
```

`connectionTimeoutMillis` landed at 10s rather than the 5s first sketched here:
a Neon compute cold-resume after autosuspend can take several seconds, and 5s
risked converting a resume into a spurious failure.

**One trap found while implementing.** `getPrisma()` in `packages/db` also backs
one-shot CLI work (seed scripts, backfills), and node-postgres keeps _both_ the
idle socket and its expiry timer ref'd. Raising the idle timeout to 60s would
therefore have made every script hang a full minute at exit. Measured, with a
15s idle timeout and no mitigation:

```
allowExitOnIdle=false   process exited after 15,064ms
allowExitOnIdle=true    process exited after     42ms
```

`allowExitOnIdle: true` is set on the `packages/db` pool only. Long-lived
services are unaffected — their listening socket keeps the process alive
regardless — so they keep warm connections while scripts still exit promptly.

Still open, deliberately not bundled: Cloud Run sets no
`max_instance_request_concurrency`, so its default of 80 concurrent requests per
instance sits well above `max: 10`. Harmless at current volume; worth aligning.

**Risk:** low–medium. `connectionTimeoutMillis` is the one value that can surface
a _new_ error rather than only removing work.

**Verify:** `pg.connect` count collapses while `pg-pool.connect` stays roughly
flat; `pg-pool.connect` p95 falls from 64ms toward its 0.52ms p50.

### 2. Ship the two fixes already written — COMMITTED, NOT DEPLOYED

Both exist and are undeployed. Together, **64,450 stmts/week, 40% of all real SQL.**

- **JobRun tracker** (uncommitted, `apps/jobs/src/lib/postgres-job-run-tracker.ts`)
  — removes the SELECT (11,350), DELETE (11,260), BEGIN (12,310) and COMMIT
  (12,300) = **47,220 stmts/week, 29.5%**. The old `record()` wrapped
  `$transaction(findMany + deleteMany)`; that is precisely what those BEGIN/COMMIT
  spans are.
- **PlatformSetting cache** (`aabb3f9a`, undeployed) — **17,230 stmts/week, 10.7%**.
  The corrected rate is ~1 read per request, not the ~2 the commit message
  claims; same double-counting.

**Risk:** low, both written and reviewed. The awkward part is staging them out of
a tree carrying ~465 unrelated uncommitted entries.

**Verify:** `SELECT JobRun` / `DELETE JobRun` go to ~0, `BEGIN` on
`POST /jobs/:name` to near zero, PlatformSetting reads fall to roughly one per
instance per 60s.

Committed as `f4b1e981` (JobRun). The PlatformSetting half needed no commit —
`aabb3f9a` was already on main and correctly wired; it is applied in the API
composition root only, which is right: **100% of PlatformSetting reads come from
`GET /trpc/:path`**, zero from jobs, so api-only captures the whole 17,230/wk.

**Deploy ordering matters.** The daily `jobs.prune-run-history` Cloud Scheduler
job is generated from `jobs.manifest.json` by terraform. Apply terraform before
or with this code — ship the code alone and `record()` stops pruning while
nothing else starts, so `JobRun` grows unbounded.

**Blocker found, not ours.** `pnpm -C apps/jobs validate:manifest` fails at HEAD:
the manifest still lists queue entry `settlements.execute-transfer`, whose
handler was deleted in the ledger cutover (`apps/jobs/src/jobs/settlements.ts`
says so at HEAD). Proven pre-existing — `settlements.ts` is byte-identical to
HEAD and the manifest diff contained only the prune-run-history addition. The
pre-commit hook runs this check whenever anything under `apps/jobs/` is staged,
so it blocks every commit to that app until the dead queue entry is removed.
Left alone here because it is settlement territory with in-flight uncommitted
work.

### 3. Skip the COUNT when the caller does not want it — COMMITTED, NOT DEPLOYED

`packages/adapters/src/db/prisma/events.ts:2034`

Saves 12,360 statements **and** 12,360 pool acquisitions/week (7.7%).

```ts
const [total, events] = await Promise.all([
  p.event.count({ where }),           // ← never reaches the caller
  p.event.findMany({ where, ... }),
]);
```

For `listEventsByCountry` the total is dead: the use case returns
`{ events: mapped }`, the tRPC output schema is `z.object({ events: ... })`, and
`paginated.pageInfo.total` feeds exactly one thing — a log line's `total:` field.

Not a deletion: `discover-public-events.ts` calls the same repo method and does
return `total`. Add `includeTotal?: boolean`; `listEventsByCountry` passes false,
`discoverPublicEvents` keeps true.

For the record, the SearchDocument CTE already solves this the right way with
`COUNT(*) OVER()::int AS "totalCount"`. Only the Prisma path pays for a second
query.

**Risk:** low. The only behaviour change on `countryEvents` is a log field.

Committed as `826035ef`. Measured against the real adapter and the local dev
database:

```
default / includeTotal:true   4 statements, 1 COUNT, total=34, hasNextPage=true
includeTotal:false            3 statements, 0 COUNT, total=12, hasNextPage=false
```

Page contents identical (12 items) either way. When the count is skipped `total`
becomes a lower bound rather than a fabricated figure, so `hasNextPage` reports
false instead of inventing a page count — documented on the port, and the
`total:` log field is dropped rather than left reporting a bound as a total.

`listPublishedByRegion` has the identical shape and was left alone: its caller
does read the total, and production shows no matching count volume.

**Verify:** `SELECT COUNT(*) Event` drops ~50%; the discover path keeps its share.

### 4. Cut homepage origin renders — DONE (local, undeployed), by a different route than scoped

The biggest single remaining lever, ranked below #3 purely on risk and effort.

`GET /trpc/:path` is 50% of all real SQL, and 98.7% of it is one homepage bundle
whose cache key space is a handful of country codes. A read-through cache on
`countryEvents` / `featuredEvents` at 60s TTL would collapse most of it.
`withCachedPlatformSettings` is the proven in-repo pattern and Redis is wired.

**Risk:** medium — staleness on a discovery surface, and it needs invalidation on
publish. Given the traffic looks ~90% automated, the audience for 60s-fresh
homepage data is mostly crawlers.

**What actually shipped, and why not an API-layer cache.** The home page is
already edge-cached: `cf-cache-status: HIT` with a rising `age`, because
`cloudflare-cache` sets `cache = true` with `edge_ttl.mode = "respect_origin"`,
which overrides the origin's `no-store`. So origin renders are governed by the
**revalidation clock, not by traffic** — extra crawler hits against an already-hot
colo cost nothing. An API-layer cache would have sat behind a cache that was
already absorbing the requests; raising the TTL was the actual lever.

Three things landed:

1. **Edge TTL 60s → 300s.** Set in `apps/web/next.config.ts` (`source: "/"`),
   NOT in `page.tsx`. `export const revalidate` is inert on that route — the SSR
   tRPC client's header callback awaits `headers()`, so Next's route cache never
   engages, and the `Cache-Control` Cloudflare honours comes from the config
   rule. The giveaway was the live `stale-while-revalidate=120`, which
   `revalidate = 60` cannot produce.
2. **The home page no longer varies on `CF-IPCountry`.** There is no custom
   cache key (and Cache Rules custom keys are Enterprise-only), so varying the
   HTML per viewer meant whichever viewer warmed a colo decided what everyone
   behind it saw. SSR now renders one fixed country (`HOME_SSR_COUNTRY`);
   viewers are personalized client-side from `navigator.language` exactly as
   before. Also collapses N per-country entries per colo into one.
3. **The SSR prefetch was never being read.** The server seeded React Query with
   lowercase `"us"`; the client queries uppercase `"US"` from
   `inferCountryCodeFromNavigator`. Different keys, so the prefetch was fetched,
   serialized into the payload, and discarded — the client refetched both
   sections on every load. Normalized, and pinned by
   `apps/web/src/server/__tests__/home-discovery.test.ts`, verified to fail when
   the old lowercase value is planted back.

**Still open:** there is no CDN purge, so 300s is now the ONLY freshness control
on the home page. Piece 1 of the original scope (Cloudflare purge-by-URL on
publish) was deliberately not done — the home page goes stale on event _publish_,
which happens in the API, so it needs a port, an adapter, a `CLOUDFLARE_API_TOKEN`
secret and terraform. `events/category/:slug/:city` has run at 3600 without a
purge for some time, so this is consistent with existing practice rather than new
risk.

**Verify:** tRPC GET db spans per transaction approach zero on cache hits.

### 5. Enable `relationJoins`

`packages/db/prisma/schema.prisma:7`

Saves 26,500 statements **and** 26,500 pool acquisitions/week (16.5%) by folding
the two `IN (NULL)` relation round-trips into the parent query.

`relationLoadStrategy` is still a preview feature in Prisma 7.1.0 — confirmed in
the installed generator source, `node_modules/@prisma/client/generator-build/index.js:7670`.
The schema carries only `["postgresqlExtensions"]`, so the option does not exist
in the generated client at all.

Measured against local Postgres with the same adapter, reproducing the prod SQL
byte-for-byte including its trailing `OFFSET $n`:

```
preview OFF (== prod today):  3 statements,  4 pool acquisitions,  3 TCP
preview ON  (default):        1 statement,   2 pool acquisitions,  2 TCP
preview ON  + explicit join:  1 statement    (identical SQL)
```

Results compared byte-identical across mixed null and non-null relations.

**Risk: medium–high, and the reason it sits here rather than at #3.** The flag
flips the _default_ strategy to `join` for every relation read in the repo — note
that "preview ON, no explicit option" already produced one statement. Prisma's
`join` strategy also gives up the `IN`-list batching that can win on wide
fan-outs, so some queries may regress. Repo-wide behavioural change, not a local
opt-in.

**Verify:** both `IN (NULL)` queries vanish; watch p95 on unrelated
relation-heavy admin reads for regressions.
